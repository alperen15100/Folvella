# Trendora publishing workflow

1. Read current posts and `data/trend-research.json` before choosing a topic. Do not publish the same search intent twice.
2. Use ONLY official Pinterest Trends and official Pinterest editorial pages for topic research. Never use third-party articles, stock photography or other sites' images. A public page that exposes no trend data is not evidence of growth. Distinguish searches, Pin saves and outbound clicks; annual forecasts are not current daily viral evidence. Record the query, source URL, period, region if available, checked date and evidence type. Do not invent growth percentages, views or saves. Seasonal suggestions are labeled as editorial opportunities in the research record.
3. Publish one or two useful English articles per run only when there is a meaningful new opportunity. Preserve the Tier-1 lifestyle focus. No scraped or lightly rewritten articles. Write all prose originally; never copy or paraphrase another article. Only official Pinterest links may appear as trend attribution. Do not expose internal trend scores on the public magazine.
4. Generate distinct, relevant original illustrations for new covers and illustrated sections. Save optimized local WebP assets in `assets/generated/` and record their intrinsic width/height in `data/image-dimensions.json`. Explain AI-generated imagery on applicable articles. A repeated crop or unrelated stock photo is not a distinct example. Do not promise a numbered image gallery without matching examples.
5. Update `data/posts.json` with complete text, distinct slug, actual publication/update dates, descriptive alt text, useful FAQs and official Pinterest source links, if needed. A `sources` entry contains `title`, `url`, and `accessed`; a FAQ uses `q` and `a`. Set `generatedImages: true` when applicable. Never advance dates without a substantive edit. When replacing an image listed in `data/image-manifest.json`, update its path and SHA-256 entry so integrity checks continue to match the current asset.
6. Run `python scripts/build.py`. This regenerates static article/category HTML, canonical metadata, BlogPosting/Breadcrumb/FAQ schemas, crawlable home cards, related links, image sitemap and RSS.
7. Run `python scripts/validate.py`, syntax checks and inspect desktop/mobile output. Inspect generated imagery. Commit all related pages and assets together to main without overwriting concurrent changes. GitHub Pages serves the repository; confirm deployment before reporting content as live.
8. Summarize actual published URLs and limitations. No promised Google rankings. FAQ markup and llms.txt do not guarantee rich results or AI citations. Do not manufacture hreflang without genuine translations, reviews, backlinks or product structured data without products.

If shell push credentials are unavailable, use the authorized GitHub connector to create binary blobs (base64), a tree on the current branch tree, a commit and a non-forced ref update. Keep all changed files in one commit. Read the current main ref before publishing and do not force push.
